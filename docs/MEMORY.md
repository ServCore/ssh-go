# ssh-go 内存验证

日期：2026-10-16；正式工程 `worklane-ssh`，不涉及学习工程。

## 改动

文件列表由 `ref<FileEntry[]>` 改为 `shallowRef<FileEntry[]>`。目录加载、刷新和文件操作后整体替换后端快照；筛选和排序仍产生派生列表，不直接修改文件项。选择集合和两个面板传递的状态同样整体替换。这样虚拟列表只需要跟踪快照和选择的变化，不必为目录中的每个对象创建代理与属性依赖。

设置、服务器编辑、凭据输入、转发、传输队列、命令搜索和弹窗组件延迟到使用时加载。终端原有 3000 行回滚、多会话切换和连接功能保留。

## 前端受控对比

使用同一台 Mac 的同一个 Chrome 可执行文件、1280 × 820 窗口和 Vite 生产资源。IPC 使用隔离测试数据，本地和远程各生成 100000 个文件。每个阶段等待两次绘制，然后通过 CDP 执行两次 GC，再读取 `Runtime.getHeapUsage`。各版本分别运行 3 次，下表为中位数；MiB = 1048576 字节。

| 阶段 | 优化前 JS 堆 | 优化后 JS 堆 | 减少 |
| --- | ---: | ---: | ---: |
| 连接首页 | 2.72 MiB | 2.64 MiB | 3.2% |
| 单终端 | 4.34 MiB | 4.32 MiB | 0.4% |
| 双栏各 10 万项目录 | 142.28 MiB | 34.07 MiB | 76.1% |
| 移除已打开文件面板的会话后 | 12.77 MiB | 4.74 MiB | 62.9% |

这些数字描述 Chromium 的前端 JS 堆，不包含浏览器引擎、Go、原生窗口、GPU 和全部字节缓冲，不能换算为整个桌面应用降低 76.1%。生产入口 JS 从 219.53 kB 减到 166.81 kB，是加载量变化，也不当作内存节省。

原始结果位于 `frontend/.test-artifacts/memory/before-{0,1,2}.json` 和 `after-{0,1,2}.json`。该目录被忽略，不会提交测试机器状态。后续命令默认将新结果写入 `current-{0,1,2}.json`：

```sh
SSH_TOOLS_CHROMIUM='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' make memory
```

测试使用 1422 端口运行生产预览，验证每个面板实际具有 100000 项、渲染行数少于 100、会话移除后终端和表格卸载，并设置 80 MiB 的宽松 JS 堆上限，以捕获误用深层响应式导致的回归。测试中的强制 GC 仅用于对比，不在应用运行时执行。

## macOS 原生观察与采样口径

优化前后分别重新启动构建的 `ssh-go.app`，保持连接首页且无活动 SSH 会话，使用 `vmmap -summary` 记录实际进程。主进程物理占用分别约 28.6 / 29.7 MiB，WebContent 约 68.0 / 67.9 MiB；GPU 约 16.1 / 23.2 MiB，网络进程约 6.1 / 6.3 MiB。原始快照为 `frontend/.test-artifacts/memory/native-{before,after}-*.txt`。

这只是各一次桌面空闲快照，窗口焦点、绘制、缓存和系统内存压力会产生波动；本轮未测得显著的空闲总占用降低。主要收益来自大目录。WebView 与原生框架仍构成固定开销。

旧状态栏使用 `getrusage.Maxrss`，它是历史峰值 RSS。现在 macOS 使用 `proc_pid_rusage` 的当前 `ri_phys_footprint`，Linux 从 `/proc/self/statm` 读取当前 RSS。原生桌面上已核对状态栏约 30 MiB 与主进程 `vmmap` 物理占用相符。当前值不包含 WebView 进程；原生采样不可用时明确标记峰值回退，无 CGO 的 macOS 后端也使用此回退。其他平台明确标记 Go 运行时保留内存。

因此，旧状态栏约 103 MiB 变为约 30 MiB 是统计口径修正，不是节省了这部分内存。

## 2026-10-23：SFTP 选择与刷新调度

本轮优化大目录刷新计算和重复目录读取：

- 刷新保留选择由「每个选中项遍历新目录」改为遍历新目录并查询已有路径集合，从最坏平方级降为线性；消失的文件自动取消选择，搜索、排序和同目录滚动位置保留。
- 传输结果携带明确的目标端点。首次完成时只通知目标目录，不再通过全局完成数量刷新所有面板；重复完成通知和启动时的历史记录不触发读取。
- 连续完成合并到 120 ms 的刷新窗口。隐藏会话或窗口只标记目录需要刷新，再次显示时读取一次；正在读取时又有完成通知，结束后补一次读取，避免并发刷新或遗漏新文件。失败不会自动循环重试。
- 本地目录为共享文件系统，显示同一目录的其他会话也会标记为需要刷新；其他远程会话和无关目录不会重新读取。

当前生产资源使用相同 Chrome、1280 × 820 窗口和隔离 IPC 数据执行 3 次。双栏各 100000 项，刷新耗时为全选后点击刷新至面板恢复可用，包含自动化操作与渲染开销，不包含真实磁盘或网络耗时。中位数如下：

| 指标 | 中位数 |
| --- | ---: |
| 本地 10 万项全选后刷新并保留选择 | 100.8 ms |
| 远程 10 万项全选后刷新并保留选择 | 89.0 ms |
| 双栏各 10 万项、全选前 JS 堆 | 33.99 MiB |
| 全选并刷新后关闭会话的 JS 堆 | 4.79 MiB |

原始结果为 `frontend/.test-artifacts/memory/sftp-optimized-20261023-{0,1,2}.json`。本轮没有测量优化前全选刷新耗时，因此不报告加速倍数；这些数值仍只代表 Chromium JS 堆与模拟目录读取，不代表桌面总内存或真实 SSH 延迟。性能回归保留 80 MiB 堆上限，并增加每栏 5 秒的宽松全选刷新预算，以捕获平方级计算回退。

前端类型检查与构建、`go vet ./...`、Go 竞态测试、62 项界面回归和上述 3 轮性能测试通过。新增回归覆盖端点隔离、批量合并、隐藏窗口与会话、关闭后清理、读取期间的完成通知、失败后恢复、迟到的历史记录以及目录切换。
